01 · The stack

What each piece is actually for

Naming tools is not a process. This is the job each one does, and the reason it is in the list.

Figma, over MCP
Still the record, but now a readable one. An agent can pull frames, variables and component properties out of the file, and write new frames back into it.
HTML
Where the flow gets decided. A prototype in code answers what a frame cannot: what happens on the third tap, what the empty state feels like, whether the copy fits.
Claude Code
Reads the repository, writes the prototype, drives the Figma calls, and reviews its own output when I tell it to.
GitHub
Everything lands here. Prototypes, specs, token files, this website. Versioned, reviewable, and readable by whatever builds next.
DESIGN.md and tokens
The spec, in a form a coding agent consumes on every build. Handoff stopped being a phase, because nothing ships off-system.
Skills
Rules the model has to follow. The voice system is one: product, agent and status tiers, so screen copy is generated to the spec rather than written and then corrected.
02 · The loop

I almost never start from a blank page

Work starts as an artefact plus a link. An existing prototype and the frame it came from. A page in the live product. A repository I can read. I design against something that already exists, because the thing that usually breaks a design is not the idea. It is the data underneath it.

So I go to the source system rather than to the document describing it. If the question is how something behaves, I open it and do the thing.

The loopthe artefact is the brief
artefact + link→HTML prototype→put it in front of people→back-port to Figma→tokens and DESIGN.md→an agent builds it

The order matters. The prototype is where the flow gets settled; the frames catch up afterwards, once there is something worth recording.

If doing this is easier and faster for you in HTML, then just do it there. We can update the Figma later.

03 · Figma over MCP

The design file became something you can query

Most people use the Figma MCP server one way, to generate code from a frame. I use it three ways, and the other two are where the value is.

Reading
Pull the real component names, variant properties and variable bindings out of the file, so a prototype is built from what exists rather than from a screenshot of it.
Writing
Build native frames from a prototype we have already agreed on, so the record catches up with the decision instead of blocking it.
Auditing
Check that a frame is bound to tokens rather than to pasted hex values. That failure is invisible until the day a theme changes, and then it is everywhere.

I also watch what it costs. I have gone back over a session to count how many MCP calls it burned, because a workflow that is elegant and slow does not survive a deadline.

04 · The room

The research is not generated

The redesign that cut customer service calls at ICICI Lombard was built on sessions with 14 users and 38 stakeholders. I wrote the scripts and moderated them. I still write the run-book, still moderate, still sit through the silence while someone fails to find the thing I was certain was obvious.

What AI does here is the work around the room. A first pass at the script. The tidy-up of a transcript. A sweep of tags across sessions, and then an argument with me about what the tags actually mean. The findings stay mine, because the room was.

A model can tell you what people said. It cannot tell you what they meant, because it was not there when they hesitated. Every study I have run turned on something that happened between the questions.

05 · Review

I make it argue against me

The most useful instruction I give a model is to attack the work. Before I defend anything, I run an adversarial pass over it: a set of language rules, a hierarchy model, a page like this one. The prompt is a question rather than a request. Will these rules fail, and where?

It is the cheapest critique available and the only one with no ego in it. Most of what comes back is noise. The one paragraph that is not is worth the pass.

The case studies on this site went through it. Each was written, then read by three separate critics, one for facts, one for the decisions, one for voice, and rewritten against what they found. Then a linter checked the markup, the image dimensions, the sentence lengths and the spellings before anything shipped.

07 · Limits

What it does not do

  • It does not decide. Almost every correction I make to generated work removes something. Fewer steps, fewer labels, fewer words. Subtraction is a judgement about what matters, and nothing in the model has a stake in the answer.
  • It does not sit in the room. See 04.
  • It does not know what the business will not fund. The constraint that kills a design is usually political, and it is never written down anywhere the model can read.
  • It does not name things well. Naming is structure, not decoration. What a thing is called decides what people believe it does, and that call has stayed mine every time.

None of this is an experiment. It is how the work gets made now, on a deadline, with my name on the result. The page you are reading was made this way, and so was everything it links to.
